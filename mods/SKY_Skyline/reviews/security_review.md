# SKY_Skyline security review (security-auditor)

Date: 2026-10-05. Scope: `addons/sky_scripts/**` (elevator, keycard door, keycard item, actions, rate limiter), `addons/sky_towera/config.cpp` + `model.cfg`, `addons/sky_items/config.cpp` (generated by `assets/gen_configs.py` from `assets/skyspec.py`), and repository / key hygiene.
Vanilla reference: DayZ 1.29 scripts (`scratchpad/dzs/scripts`). Paths below are relative to that tree (`v:`) or to `mods/SKY_Skyline/addons/sky_scripts/scripts/4_World/SKY/` (`mod:`).

## 1. Design claim: checked against the vanilla code

| Claim | Verdict | Evidence |
|---|---|---|
| No custom RPCs | **True** | The mod has no `OnRPC`, `ScriptRPC` or `RPCSingleParam` (grep over `sky_scripts`). The only server-to-client traffic is vanilla `NotificationSystem` and net-sync vars. |
| The server re-runs ActionCondition | **True** | `v:4_world/classes/useractionscomponent/actionmanagerserver.c:142` runs `pickedAction.Can(m_Player,target,item)` before it accepts the action. `actionbase.c:873-916` `Can()` calls the condition components and then `ActionCondition`. |
| What the client controls in an action start | action id, main item, target object, target parent, component index, cursor hit pos | `actionmanagerserver.c:44-52`, `actionbase.c:494-568` (`ReadFromContext`). |
| The server recomputes the main item from the hands | **Partly.** The client's item is used, but it must equal the item in hands. | `actionmanagerserver.c:222` passes `GetItemInHands()`, but `HandleReciveData` (`actionbase.c:571-573`) replaces it with the client's `mainItem`. The equality check `actionbase.c:181-186` only runs when `UseMainItem() && MainItemAlwaysInHands()`, and both default to true (`actionbase.c:391-399`), so `ActionSKY_SwipeKeycard` is covered. `SkyServerSwipe` checks again (`mod:Land_SKY_TowerA_Lobby.c:137`). |
| CCTCursor range is trustworthy | **False** (the mod does not depend on it) | `v:.../targetconditionscomponents/cctcursor.c:30-31` measures the distance to the client-supplied `GetCursorHitPos()`. The real range checks are the mod's own server-position checks (`SkyIsNear` / `SkyIsInCab` in `mod:Land_SKY_TowerA_Core.c:126-150`, `SkyIsNearDoor` in `mod:Land_SKY_TowerA_Lobby.c:163-167`) and `IsInReach` (`actionbase.c:1181-1210`, which uses the server-side selection position of the component). |
| Forged component index or target | **Safe** | `GetDoorIndex` is native and server-side. `SkyRequiredTier` fails closed for -1, for unresolved doors and for non-keycard doors (`Lobby.c:92-98`). `doorIdx >= GetDoorCount()` is rejected (`Lobby.c:135`). Distance is measured to *that* door's soundPos (`Lobby.c:139`). A forged elevator target must be a `Land_SKY_TowerA_Core`, and every check uses the player's position in *that* building's frame. |
| The client never sends a floor | **True** | One action class per command (`ActionSKY_Elevator.c`). The action id is checked against registered actions (`actionmanagerserver.c:47-49`). The source level comes from the server position (`Core.c:114-123`) and the target from config (`Core.c:152-163`). |
| No vanilla action opens a locked keycard door | **True** | `ActionOpenDoors` calls `CanDoorBeOpened(idx, true)`, which is false while the door is locked (`actionopendoors.c:43`, `3_game/entities/building.c:130-139`). Lockpick unlock/lock needs `tool.GetKeyCompatibilityType() & building.GetLockCompatibilityType(idx)` (`actionunlockdoors.c:38`, `actionlockdoors.c:39`), and the mod returns `EBuildingLockType.NONE` = 0 (`Lobby.c:105-110`, `3_game/enums/ebuildinglocktypes.c:3`), so the AND is 0 for every tool, modded ones included. `ActionLockedDoors.OnExecute` calls `OpenDoor` on a locked door (`actionlockeddoors.c:43`). That is the engine "rattle" path that every vanilla locked door relies on. The only other unlock path is the debug action under `#ifdef DIAG_DEVELOPER` (`actiondebug.c:14`, `building.c:233-235`), which exists only in the Diag exe. |
| `LockDoor(idx, true)` closes and locks | **True** | `building.c:55`: "Locks the door if not already locked, resets the door health. 'force = true' will close the door if open". |
| Elevator doors can't be driven by vanilla door actions | **True** | `Land_SKY_TowerA_Core` has no `class Doors` (`sky_towera/config.cpp:78-138`). Its doors are `user` animation sources set only by script, so `GetDoorIndex` returns -1. |
| Server-side `SetPosition` teleport is a vanilla pattern | **True** | `v:4_world/static/miscgameplayfunctions.c:1739-1750`, `developerteleport.c:141-144`. |

Conclusion: the trust model holds. I found no Critical or High issue. The remaining findings are soft-locks, griefing, and one initialisation assumption that must be verified before release.

## 2. Findings

### Critical
None.

### High
None.

### Medium

**M1. Elevator cab soft-lock: no way to open the doors from inside, and two paths leave players shut in**
`Core.c:183-199`, `Core.c:249-262`
- CALL is refused from inside the cab (`Core.c:186`), and the panel commands need `target != level` (`Core.c:194`). Nothing opens the doors from the inside.
- (a) Overload: with 5 or more players in the cab while it is IDLE (doors closed after the 8 s auto-close), every panel request returns "Overloaded" without opening the doors (`Core.c:258-262`). Nobody inside can open them. If nobody calls the car from outside, those players stay shut in.
  - A griefer can cause this deliberately. Unconscious players count toward capacity because `SkyOccupants` only checks `IsAlive`.
  - If the state was OPEN when this happens, `SkyAutoClose` has already been removed at `Core.c:249`, so the doors stay open until the next request.
- (b) Logout: a player logs out in the cab at level L, then the car leaves L. Logged-out players are not in `GetPlayers`, so they are not teleported with the car. On login they are in a closed cab room at L while `m_SkyCarLevel != L`. The panel is refused (`Core.c:194`) and CALL is refused (`Core.c:186`), so they stay stuck until someone calls the car to L.
- Fix:
  - Add an `ActionSKY_ElevatorOpen` command, or allow CALL from inside the cab. On the server, treat it as "car to my level and open". When `SkyIsInCab(player, level)` and the car is elsewhere, send the car to `level`.
  - In the overload branch of `SkyServerRequest`, do the same as `SkyDepart`: `SkySetState(OPEN, true)` and re-arm `SkyAutoClose`.

**M2. Security-room trap: a tailgater without a card cannot leave**
`Lobby.c:153-174`, `skyspec.py:139-147`
- After a swipe, the door stays unlocked and open for `skyKeycardRelockMs` = 60 s (`sky_towera/config.cpp:53`). Then `LockDoor(idx, true)` force-closes and locks it (`Lobby.c:169-174`).
- The room has a single door and glass/concrete walls. A player inside without a T2+ card can only trigger the vanilla rattle (`actionlockeddoors.c:43`). After logging out they reconnect still inside.
- A card holder can therefore lure players in and leave them locked in.
- Fix: add an unauthenticated exit. For example, accept `SkyServerSwipe`-like requests with no card when the player's model-space position is inside `SECURITY_ROOM` (a server-side check in `WorldToModel`). Alternatively, show an "Exit" action for the keycard door only on the inside. Keep tier checks for entering.

**M3. Lock state and limiters depend on `EEInit`, and the door fails open if `EEInit` does not run**
`Lobby.c:68-78`, `Core.c:75-87`
- The keycard door is locked only by `SkyLockAll`, which is scheduled from `EEInit` on the server. The rate limiters are also created only there.
- Vanilla static map buildings initialise server state in `DeferredInit` and register themselves with `g_Game.RegisterNetworkStaticObject(this)`: `land_warheadstorage_main.c:58-60`, `land_underground_entrance.c:238`. A comment in vanilla also notes engine callbacks "not being called on static objects" (`land_underground_entrance.c:76`).
- The CE loot points (`mapgroupproto`, `skyspec.py:151`) suggest the towers are meant to be placed as static terrain objects. If `EEInit` does not run for that placement:
  - The door is never locked, so anyone can open it with vanilla `ActionOpenDoors`. This is a full keycard bypass and would be High.
  - `m_SkySwipeLimiter` and `m_SkyPlayerLimiter` stay null, so swipes and elevator requests hit null-pointer errors on every attempt.
  - Net-sync variables may not replicate.
- Fix:
  - Lock in `DeferredInit()` on the server (override, call super) as well as in `EEInit`, and call `RegisterNetworkStaticObject(this)` there.
  - Create the limiters in the constructor, or create them on first use.
  - Remove the pending `SkyLockAll` call in the destructor (today only `SkyRelock` is removed, `Lobby.c:39`).
  - Release gate: QA must confirm in a dedicated-server test that the door is locked after a restart for the placement method actually used (static terrain object, `objectSpawnersArr`, or init.c `CreateObject`).

### Low

**L1. Explosion damage is not zeroed on the keycard door zone**
`sky_towera/config.cpp:57-73`, generator `gen_configs.py:69-90`
- The armor sets `Projectile` and `Melee` to 0, but there is no `FragGrenade` class, which is the explosion armor type. Grenades, IEDs and plastic explosive therefore damage the `door_sec` zone at the default coefficient.
- `building.c:55` ("LockDoor ... resets the door health") shows the engine tracks door health together with the lock. I could not confirm from the scripts whether a door at 0 HP becomes passable.
- Fix: add `class FragGrenade { class Health { damage = 0; }; class Blood { damage = 0; }; class Shock { damage = 0; }; };` to both `GlobalArmor` and the door zone's `ArmorType`. Then test with a grenade or explosive in-game. If the door opens at 0 HP, raise this to High.

**L2. CALL hijack and capacity gaps**
`Core.c:251-283`, `Core.c:299`
- Anyone on any floor can CALL the car, and that moves its occupants to the caller's floor, which enables ambushes. Restrained and unconscious occupants are moved as well.
- Capacity is checked at departure (`Core.c:273`), but the arrival teleports whoever is in the cab volume at that moment (`Core.c:299`). A player standing in the door line who is pushed in by the closing doors is therefore carried beyond the limit.
- Two players taking turns calling can keep the car busy, because the 4 s cooldown is global (`Core.c:241, 265`).
- Impact is limited because the stairs are always available.
- Fix:
  - Snapshot the occupant list in `SkyDepart` (store the `PlayerBase` refs) and teleport only snapshotted players who are still in the cab at arrival.
  - Optionally refuse a remote CALL while the car has occupants and its doors are open.

**L3. Teleport robustness**
`Core.c:299-309`
- Raw `p.SetPosition(dst)` is used without vanilla's root-object logic (`developerteleport.c:85-110`: vehicle or unconscious parent).
- Players in the middle of an action or with a parent object are moved anyway.
- Fix: skip any occupant with `p.GetParent()` set or `p.GetCommand_Vehicle()`. Interrupt the current action first with `p.GetActionManager().Interrupt()`.

**L4. Denial path cost**
`Lobby.c:112-122`
- The notification is sent on every rejected swipe, which is bounded by the 1.5 s swipe limiter. The log is bounded at 5 s per identity.
- Each building keeps two maps of at most 512 entries (`SKY_RateLimiter.c:99-119`).
- This is acceptable. I note it only so a later refactor does not move the notification before the limiter.

### Info

- **I1. Notifications.** A null identity broadcasts to every player (`3_game/client/notifications/notificationsystem.c:135`). The mod guards against this correctly (`Core.c:218`; the identity is checked at `Lobby.c:127` before `SkyDeny`). Keep the guard when refactoring.
- **I2. Admin log.** Each ride writes `PlayerTeleportedLog` lines (`Core.c:307-308`, vanilla `pluginadminlog.c:434-438`). That is good for auditing, but third-party ADM-parsing anti-teleport tools will see one entry per occupant per ride. Server owners should whitelist the reason prefix `SKY elevator`. Denial lines include the client-chosen Steam name through vanilla `GetPlayerPrefix`, which is the same as vanilla behaviour.
- **I3. BattlEye.** DayZ BattlEye has no Arma-style user-editable script or remote-exec filters to update. With no custom RPCs and no dynamic script execution, server owners need no exception. Teleports are server-authoritative `SetPosition`, the same mechanism vanilla uses for contaminated-area and restricted-area relocation (`miscgameplayfunctions.c:1707`, `playerbase.c:7219`).
- **I4. Debug paths.** The mod has no `#ifdef DIAG*` code, debug RPCs or admin shortcuts. The vanilla Diag-only `ActionDebug` can unlock any door (`actiondebug.c:14`, `building.c:233-235`), so never run DayZDiag as a public server. `-filePatching` is not required, because `CfgMods` uses the PBO prefix paths (`sky_scripts/config.cpp:23,28`).
- **I5. Repository and key hygiene: OK.**
  - `mods/SKY_Skyline/` is still untracked (`git status`).
  - There are no `*.biprivatekey`, `*.bisign`, `*.bikey`, `*.pbo` or `workspace.config.json` files in the mod or in history (`git log --all --diff-filter=A`).
  - There are no secrets, passwords or webhooks in `.py`, `.c`, `.cpp`, `.json` or `.cfg` files.
  - `__pycache__/` and `*.pyc` are ignored (`.gitignore:31-32`). `build_stats.json` holds only triangle counts.
  - `core.hooksPath=.githooks` is set, and `pre-commit` is executable (mode 100755) and covers keys, PBOs and local configs.
  - On the first commit, `*.p3d` goes through LFS (`.gitattributes:17`).
- **I6. Noticed in passing (functional, not security).**
  - The keycard config points to `SKY_Skyline\sky_items\data\sky_keycard.p3d`, but the file is `addons/sky_items/sky_keycard.p3d`.
  - The `sky_keycard_t*_co.paa` textures are not present yet.
  - `ActionSKY_SwipeKeycard` uses `CCINonRuined`, so the server-side "card damaged" deny (`Lobby.c:143-147`) is unreachable. That is harmless.

## 3. Verdict

The trust model is sound: actions are re-validated by vanilla `Can()`, and the mod re-checks identity, position, state, hands and tier on the server. No client-controlled value picks a floor, a class or a log format.

M3 has to be verified on the real placement before release. If the door turns out not to lock, M3 becomes a blocking High.

GATE: PASS
